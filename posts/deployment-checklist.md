## 先定义成功的样子

开始部署前，先写下最终需要交付的行为。例如：通过指定域名访问首页，页面资源正常加载，并且关键操作能够完成。

这样的目标比“安装软件并启动服务”更具体，也更容易验证。

## 从本机服务开始

在使用 systemd 的 Linux 系统上，可以先检查目标服务的状态与日志。下面用 `example.service` 代表实际服务名，执行时需要替换。

```bash
systemctl status example.service
journalctl -u example.service -n 50 --no-pager
```

状态用于确认进程是否运行，日志用于理解启动过程和请求错误。只看到 `active`，还不能说明所有依赖都已经就绪。

## 验证请求经过的路径

访问链路可能经过域名解析、反向代理、应用服务和数据存储。沿着实际请求路径逐段检查，比同时改动多处配置更容易定位问题。

如果应用监听在本机的 8080 端口，可以先检查它的响应：

```bash
curl -I http://127.0.0.1:8080/
```

然后再使用真正准备交付的地址发起请求。部分服务不支持 HEAD 请求，此时应使用普通 GET，并检查返回内容。

## 打开页面，完成一次实际操作

对于网页，HTTP 状态正常只是一个检查点。还应查看样式、脚本和图片是否成功加载，以及关键路径是否能够走通。

对于接口，除了状态码，还要检查响应数据是否符合业务预期。空对象、默认页面或反向代理的欢迎页，都不等于应用本身已经工作正常。

## 留下可以复查的结果

记录访问地址、验证时间、关键结果和仍未解决的问题。遇到失败时保留原始错误，避免只写一句“网络问题”。

部署完成的判断，应回到最开始定义的目标：使用者能否通过预期入口，得到预期结果。
