## 一次提交说明一件事

当功能修改、格式调整和无关清理混在一起时，阅读差异会变得困难。尽量让一次提交围绕一个能够清楚描述的目的展开。

这不代表每一行代码都要单独提交。更实用的标准是：这组修改能否作为一个完整的意图被理解。

## 提交之前，先读差异

下面三个命令分别用于查看工作区状态、尚未暂存的修改，以及已经准备提交的修改。

```bash
git status --short
git diff
git diff --cached
```

检查的重点不是行数，而是是否存在临时调试、无关文件、误删内容或不应进入仓库的本地信息。

## 选择需要暂存的内容

如果一个文件中混合了几类修改，可以交互式地选择本次需要暂存的片段。

```bash
git add -p
```

完成后再查看一次暂存区差异。不要只依赖编辑器里“文件已保存”的状态判断提交内容。

## 写清变化，也写清原因

“修改页面”能描述一个动作，但很难帮助后来的人理解问题。“调整手机端导航，避免菜单遮挡文章标题”提供了更直接的上下文。

提交说明不必很长。如果原因从差异中无法直接看出，可以在正文补充触发条件和验证结果。

## 提交之后再看一眼

```bash
git show --stat HEAD
git status --short
```

确认提交包含预期内容，并了解工作区是否还留有未提交修改。清晰的提交历史来自每一次结束前的短暂停顿。
